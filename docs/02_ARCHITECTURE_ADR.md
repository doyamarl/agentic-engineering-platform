# Architecture & ADR — Agentic Software Engineering Platform
Version: 0.1 draft | 2026-11-13 | Status: proposed

## 1. Architecture principles
Own the product domain, control plane, UX, orchestration contracts, acceptance and policy. Reuse existing agent SDKs, container runtimes, databases and CI. Prefer boring, inspectable components over generalized frameworks. Strong contracts at boundaries; no premature microservices. Every decision is backed by executable tests and architecture rules.

## 2. Logical architecture
Web (Next.js) / CLI → versioned API → modular monolith (Identity, Tenant, Mission, Workflow, Policy, Provider, Artifact, Acceptance, Audit) → PostgreSQL + durable jobs/outbox → worker → AgentAdapter → SandboxAdapter → Git/CI/QA adapters.

Execution plane runs separately from API even in Docker Compose. Agent code is untrusted relative to control plane. Tenant context is established from authenticated principal, never from client-provided tenant_id alone. Background jobs re-check permissions and tenant ownership. Audit and acceptance data are immutable or append-only. Websocket/SSE streams use scoped authorization.

## 3. Technology decisions (provisional)
- Control plane: TypeScript strict, Node LTS, Fastify, Zod/JSON Schema at ingress; Next.js for UI. Shared TypeScript reduces cognitive load; validation is required at runtime.
- DB: PostgreSQL, migrations, explicit tenant_id, composite tenant-scoped keys; use row-level security as defense in depth, not sole control.
- ORM/query: thin SQL access layer with typed queries (e.g., Kysely or generated SQL), not domain types coupled to ORM.
- Background execution: PostgreSQL-backed durable queue/outbox for v0.1; Temporal only if long-lived workflows/scale justify operational cost. Approval waits persist as DB state, not sleeping workers.
- Agent SDK: adapters for Codex and Claude, provider capabilities negotiated per task. API-key and interactive account auth are separate strategies with provider-specific terms and limitations.
- Sandbox: Docker for trusted local development only; for enterprise multi-tenant untrusted execution, require stronger isolation (dedicated VM/microVM or equivalent), per-tenant network and credentials. Docker alone is **not** an adequate hostile multi-tenant security boundary.
- Go: candidate for isolated worker/runtime daemon if measured operational benefit appears. Rust: candidate only for narrowly scoped security-critical or high-performance components after profiling. Neither required in v0.1.
- Testing: Vitest unit/contract, Testcontainers for DB/integration, Playwright for UI/E2E, security integration tests for tenant isolation.

## 4. Module boundaries
Domain packages may import standard libraries and shared primitive types only; never import Next.js, Fastify, ORM, SDK or Docker clients. Application layer depends on ports (AgentPort, SandboxPort, RepositoryPort, PolicyPort, IdentityPort, GitPort, EventPort). Infrastructure adapters implement ports. UI depends on public API contracts only. Cross-module calls use exported application services/events, not direct table access.

## 5. Provider contract and capability model
```ts
type AgentCapability = 'streaming'|'resume'|'tool-approval'|'structured-output';
interface AgentPort {
  capabilities(): Promise<ReadonlySet<AgentCapability>>;
  start(input: AgentTask, context: ExecutionContext): Promise<AgentSession>;
  events(session: AgentSession): AsyncIterable<AgentEvent>;
  cancel(session: AgentSession): Promise<void>;
}
interface SandboxPort {
  create(spec: SandboxSpec, context: ExecutionContext): Promise<SandboxHandle>;
  destroy(handle: SandboxHandle): Promise<void>;
}
```
Implementation: `packages/application/src/agents/agent-port.ts`. `start()` returns a `Result` and rejects a task whose `requires` names a capability the adapter lacks (PRD FR-03). Every adapter must pass `agentPortContract` (`@aep/application/testing`), which covers the §10 provider gate; tool approval is covered as capability negotiation until an adapter offers `tool-approval`. SandboxPort: `packages/application/src/sandboxes/sandbox-port.ts`, with `spawn()` for running a process inside the sandbox. The Docker adapter (`adapters/sandboxes/docker`, T0/T1 only) runs the host user's uid (never root) with a read-only root filesystem, `--cap-drop ALL`, `no-new-privileges`, memory/CPU/PID limits, only the checkout mounted read-write (`/workspace`) plus explicitly listed read-only mounts (e.g. a tool binary), no Docker socket, and secret values kept off the host command line. Its TTL is enforced by Docker itself (main process `sleep <ttl>` under `--rm`), so sandboxes disappear even if the worker dies. Network is `none` or an allowlist: the sandbox sits on its own `--internal` Docker network (no route out, no external DNS), and a separate hardened proxy container on that network (`egress-proxy.ts`) forwards only CONNECT tunnels to allowlisted host names on port 443, reached through `HTTPS_PROXY`. TLS stays end to end and plain HTTP is refused. The proxy exits with the sandbox TTL; the network itself remains until `destroy()` (it carries the `aep.sandbox` label for sweeping). The Claude adapter (`adapters/agents/claude`) takes an optional `sandbox`: each session then gets its own sandbox, the SDK's native Claude Code binary is mounted read-only and started there through `spawnClaudeCodeProcess`, the network allows `api.anthropic.com` plus configured hosts, the environment is fixed (no host values besides the API key), and the sandbox is destroyed as soon as the session is aborted or ends. Without `sandbox` the process runs on the host, for development only. GitPort: `packages/application/src/git/git-port.ts`; the GitHub adapter (`adapters/git/github`) authenticates as a GitHub App and requests a fresh installation token per operation, scoped to the one repository with `contents` and `pull_requests` write (GitHub expires it after an hour). The control plane, not the agent, clones, commits and pushes: the working tree is mounted into the sandbox without `.git`, the metadata stays outside it, and every git call ignores system/global config, disables hooks and fsmonitor, allows only the remote's protocol, and passes the token as an extra header through `GIT_CONFIG_*` environment variables (never argv or disk). Pushes go only to branches under `aep/` and replace an earlier attempt's push of the same mission branch; opening a draft PR returns the open one on retry. Mission planning (`packages/application/src/missions/plan-mission.ts`, job `mission.plan`): `POST /v1/missions/:id/plan` (permission `mission:plan`, mission must have a source) moves DRAFT to PLANNING and enqueues the job in the same transaction (idempotency key = mission + the version it started from, 2 attempts). The handler checks out the base branch and runs the agent with a read-only planning prompt (issue quoted as untrusted data); nothing is pushed and the scratch checkout is deleted. The agent's final message becomes the next plan version (`plans` table: append-only, row-level security, body ≤ 32,000 characters, SHA-256 checked by the database), written in the same transaction as SubmitPlan (PLANNING → AWAITING_PLAN_APPROVAL); an existing version is a Conflict. `GET /v1/missions/:id/plan` and `/plans/:version` serve it. `POST /v1/missions/:id/plan/approve` and `/plan/reject` (permission `plan:approve`) name the plan version; the decision is written to `approvals` (append-only, comment ≤ 4,000 characters) in the same transaction as ApprovePlan/RejectPlan. Approval then starts execution (StartExecution, a second transaction; repeating the request resumes it if only the approval committed). Rejection enqueues `mission.plan` again, whose prompt quotes the rejected version and the reviewer's feedback as data. Mission execution (`packages/application/src/missions/execute-mission.ts`, job `mission.execute`): `startExecution` moves an APPROVED mission to EXECUTING and enqueues the job in the same transaction (idempotency key = mission + approved plan version, 2 attempts). The handler checks out the issue's base branch, runs the agent on the working tree with the issue and the approved plan version quoted as untrusted data (a missing plan fails the mission), then the control plane pushes `aep/<mission>`, opens a draft PR and records `CompleteExecution` (EXECUTING → VERIFYING) with the PR and cost. Agent failure, timeout or no changes fail the mission; infrastructure errors throw so the queue retries; a cancellation found between steps is confirmed. CompleteExecution also enqueues `mission.verify` (`packages/application/src/missions/verify-mission.ts`), which reads the CI results of the pushed commit (GitHub check runs and commit statuses; the App token adds `checks: read` and `statuses: read`). A failed check fails the mission; pending checks are polled again as new jobs (`AEP_VERIFY_POLL_MS`, default 30 s) until `AEP_VERIFY_CI_TIMEOUT_MS` (60 min), then fail; with no CI result after `AEP_VERIFY_NO_CI_GRACE_MS` (10 min) the mission is accepted and the packet says no CI ran. On success the job builds the acceptance packet (`packages/domain/src/mission/acceptance-packet.ts`: plan version and its acceptance criteria and risks, plan approvals, pull request, changed files, CI checks, summed agent cost, residual risks) and records it with PassVerification (VERIFYING → ACCEPTANCE_READY) in one transaction (`acceptance_packets`: append-only, row-level security, JSON text with a database-checked SHA-256). `GET /v1/missions/:id/acceptance-packet` and `/acceptance-packets/:version` serve it. When the job is dead-lettered (attempts exhausted, or its worker died on the last one, in which case the queue hands it to a worker once more without running the handler), the worker's `onDead` hook (`failMissionOfDeadJob`) fails a mission still EXECUTING or confirms a pending cancellation. `POST /v1/missions` accepts the mission's `source` (a GitHub issue and base branch). The web UI (`apps/web`, Next.js) calls the same API from the server only (`app/lib/api.ts`): pages are server components, mutations are server actions (Next.js rejects cross-origin action requests), and the detail page polls a same-origin route for new events every 3 s. Each person logs in (ADR-011); the web server keeps their tokens in HttpOnly cookies and sends the access token to the API, so no token reaches browser JavaScript. It listens on 127.0.0.1 unless `HOST` is set (Compose publishes it on 127.0.0.1 only). It renders plan Markdown as text, links only https URLs, and forbids framing. Browser tests (`tools/e2e`, Playwright, run by `infra/compose/e2e.sh` in CI) drive the golden path through the UI and guard these properties, logging in as prepared accounts: a user of tenant B gets 404 for tenant A's mission; markup in titles, plans and packets stays text; non-https URLs are not links; framing is forbidden; a cross-origin server action changes nothing; the session cookies are HttpOnly and no page or response carries a token; login, the first-login password change, logout and role-based controls work. The Compose worker has no agent credentials, so the script writes the states an agent would reach (a plan awaiting approval, an acceptance packet) to the database directly. `POST /v1/missions/:id/cancel` (permission `mission:cancel`) applies Cancel as the caller: 200 when the mission is cancelled at once, 202 when running work must confirm it (the job's next step does). `GET /v1/missions/:id/events?after=<seq>&limit=<n>` serves the mission's audit trail (`mission_events`, append-only, numbered per mission) to members with `mission:read`; clients follow it by passing the last seq they saw. The worker starts the job loop only when `ANTHROPIC_API_KEY`, `AEP_GITHUB_APP_ID` and `AEP_GITHUB_PRIVATE_KEY_PATH` are set. `resume` is optional capability rather than mandatory method. Agent session IDs are opaque provider-specific values. Never pretend one provider can resume another provider's native session. Portable handoff uses explicit artifacts and summary, with loss of context declared.

## 6. Mission state machine
DRAFT → PLANNING → AWAITING_PLAN_APPROVAL → APPROVED → EXECUTING → VERIFYING → ACCEPTANCE_READY → AWAITING_RELEASE_APPROVAL → COMPLETED. Any active state can enter FAILED, CANCEL_REQUESTED, CANCELLED or BLOCKED; transitions are guarded by policy, actor and approved artifact version. Approval never grants blanket future permission. Optimistic concurrency and idempotency keys prevent double execution. Plan rejection returns AWAITING_PLAN_APPROVAL to PLANNING and requires a new plan version; like approval, it names the plan version and needs a human actor. FAILED and BLOCKED remember the state they left and return to it on Retry/Unblock; work-running states (PLANNING, EXECUTING, VERIFYING) cancel via CANCEL_REQUESTED, others cancel immediately. Implementation: `packages/domain/src/mission/state-machine.ts`.

## 7. Security threat model and controls
Threats: prompt injection from competitor pages/docs, malicious repo code, tool escalation, token leakage, cross-tenant reads, SSRF, exfiltration, CI supply-chain compromise, runaway spending. Controls: explicit trust labels on context, read-only analysis credentials, network egress allowlists, scoped ephemeral credentials, no Docker socket in agent container, non-root execution, seccomp/AppArmor where available, filesystem mount allowlists, resource/TTL caps, signed or pinned images, SBOM, secret scanning, dependency scanning, SAST, audit trails and independent security tests. Browser automation follows site policies; never bypass authentication or access controls.

Account login (ADR-011). Threats: password guessing and credential stuffing, account enumeration, theft or replay of access and refresh tokens, forged JWTs or algorithm confusion, CSRF on login and logout, OIDC authorization-code injection, mix-up and redirect manipulation, account takeover through an unverified or reassigned email claim, privilege escalation through the member API (self-promotion, removing the last admin), and passwords or tokens leaking into logs, HTML or error bodies. Controls: Argon2id password hashes; per-account lockout for 15 minutes after 5 consecutive failures; one generic error and a dummy hash check for unknown accounts; access tokens accepted only as HS256 with `iss`, `aud` and `exp` checked; refresh tokens stored as SHA-256 digests and rotated on each use, with reuse revoking the session; both tokens kept in HttpOnly, SameSite=Lax cookies set by the web server and never readable by browser JavaScript; same-origin server actions only; OIDC authorization code flow with PKCE, `state`, `nonce` and an exact redirect URI; OIDC login only for pre-registered accounts with `email_verified` true, binding (`iss`, `sub`) on first login; `member:manage` for every member change and the last admin protected; an append-only audit record of member changes and login outcomes; credential fields redacted from logs. Residual risks: no per-IP throttling yet, so guessing can lock an account for 15 minutes at a time; no MFA; an access token stays valid for up to 10 minutes after logout.

Connectors and chat (ADR-012 to ADR-014). Threats: prompt injection in data read through connectors steering the model to write tools or to exfiltrate; connector token theft from the database, logs, model context or sandboxes; a member reading another member's personal thread or personal-connection data; a malicious or spoofed MCP server; SSRF through a user-registered MCP URL; models or keys that train on inputs; a connector PR from chat that widens the platform's own permissions. Controls: connector content labelled untrusted and unable to trigger write tools without a per-call human approval; tokens encrypted at rest, used only inside the gateway, redacted from logs; RLS and API checks on thread owner and visibility; source labels and a confirmation before sharing or creating an Issue; manifest egress allowlists and per-tool allowlists; MCP URLs restricted to https outside local development; model endpoint allowlist with admin attestation; connector PRs reviewed and merged by people, with contract and egress tests in CI.

Multi-tenancy assurance tiers:
T0 local trusted operator: Docker Compose supported.
T1 trusted internal multi-user: tenant-scoped auth, DB policies, scoped workspaces, audited actions.
T2 mutually untrusted tenants: isolated VM/microVM execution, per-tenant secrets/network/storage, external security review before claiming production support.
Launch target is T1 (owner decision 2026-11-13). MVP implements T1 domain and authorization semantics; it must **not** claim T2 production security merely because tenant_id exists.

## 8. TDD and architecture enforcement
Every change: failing behavior test → minimum implementation → refactor → CI. Tests are not retroactively invented solely to satisfy coverage. Mandatory CI: formatter/linter, strict typecheck, unit and contract tests, module dependency graph check (dependency-cruiser or equivalent), migration tests, integration tests, Playwright smoke, SCA/secret scan, container scan, license audit. Merge requires green checks and review. Coverage targets are diagnostic, not substitutes for mutation/property tests. Require tenant isolation negative tests, permission matrix tests, approval-version tests, retry/idempotency tests and adversarial prompt-injection fixtures.

Coding conventions: one public entrypoint per module, no circular dependencies, no framework types in domain, no `any` without explicit waiver, exhaustive discriminated unions for state/event variants, immutable approved artifacts, strict schema versioning. Architecture test should fail if imports cross forbidden boundaries.

## 9. ADR register
ADR-001 Accepted provisionally: modular monolith + separate worker, not microservices. Revisit when independently scalable components or ownership boundaries emerge.
ADR-002 Accepted provisionally: TypeScript for UI/API/workflow; Go/Rust on evidence only. Avoid 3-language build burden.
ADR-003 Accepted provisionally: Docker Compose quickstart, PostgreSQL queue/outbox. Temporal deferred until durable orchestration complexity justifies it. Implementation: `JobQueue` and `runWorker` (`packages/application/src/jobs`), `PostgresJobQueue` on the `jobs` table. Delivery is at least once with leases (`FOR UPDATE SKIP LOCKED`, database clock, heartbeats); a worker that loses its lease cannot complete or fail the job. `(tenant, kind, idempotency_key)` is unique, so a repeated enqueue returns the existing job, and `enqueueJob(trx, …)` joins the caller's transaction as the outbox. Payloads hold identifiers only; the table has no RLS because workers claim before they know the tenant.
ADR-004 Accepted provisionally: provider capability negotiation rather than false common-denominator feature promises.
ADR-005 Accepted provisionally: tenant-first schema and authorization; isolated execution required for hostile tenants.
ADR-006 Accepted provisionally: Git-versioned Workflow-as-Code with typed manifests and schema validation; GUI editor deferred.
ADR-007 Proposed 2026-11-14 (to be implemented with the Codex adapter): agent credentials per provider. Today the worker holds one `ANTHROPIC_API_KEY` for every tenant. Proposed sources, narrowest first: a personal key the user brings (BYOK), a tenant key set by the tenant admin, and the instance key from the environment. Subscription-account login is excluded for Claude (ADR-009); for Codex it stays unverified until OpenAI's current terms are checked. Stored keys are encrypted with AES-256-GCM under an instance master key read from a file, decrypted only in the worker, handed to the agent process the way `ANTHROPIC_API_KEY` is now, and never returned by the API. Open owner decisions: whose personal key runs a mission (creator or plan approver), whether a tenant may forbid the instance key, and whether cost is reported per key owner. Update 2026-11-15 (ADR-015): with one organization per instance, the tenant key and the instance key are the same, so the sources are a personal key and the organization's key, and the question whether a tenant may forbid the instance key falls away.
ADR-008 Accepted 2026-11-13: Apache-2.0 for this repository. Third-party dependency license review remains a release gate.
ADR-009 Accepted 2026-11-13: Claude is the first coding agent adapter; Codex is the fallback. The benchmark (docs/04_AGENT_BENCHMARK.md) returned go on 2026-11-13 with `claude-sonnet-5-5`: 4 of 5 tasks accepted, cancellation and secret checks passed (docs/benchmarks/2026-11-agent-selection.md). The adapter authenticates with an API key (`ANTHROPIC_API_KEY`) only; Anthropic does not allow third-party products to use claude.ai subscription login.
ADR-010 Pending: enterprise SSO, RLS design and security isolation certification thresholds.
ADR-011 Accepted 2026-11-14 (owner decision; Sprint 4, #33): accounts and web login. Methods are `password` and `oidc`; the operator enables either or both (`AEP_AUTH_METHODS`). OIDC uses one identity provider for the whole instance, configured from the environment (issuer, client ID, client secret read from a file); per-tenant SSO stays with ADR-010. Only a tenant admin creates accounts (no self sign-up); a user belongs to exactly one tenant and the login email is unique across the instance. OIDC logs in only a pre-registered account whose email matches a verified `email` claim and binds the provider's (`iss`, `sub`) on first login; later logins match on that pair. Passwords use Argon2id from `node:crypto` (`crypto.argon2`, Node >= 24.7) with m=19456 KiB, t=2, p=1 (OWASP Password Storage Cheat Sheet, checked 2026-11-14) and are 12 to 256 characters; an initial or reset password issued by an admin is shown once and must be changed at first login. Sessions use signed tokens (owner choice over database sessions): the API issues an HS256 access JWT valid for 10 minutes (`iss`, `aud`, `sub`, `tid`, `sid`, `exp`) and an opaque refresh token (digest in `sessions`, rotated on use, 12-hour idle and 7-day absolute limits). The API still loads the membership on every request, as it does for API tokens, so disabling a user or changing a role applies from the next request; logout revokes the refresh token and the access token lapses within 10 minutes. The web server keeps both tokens in HttpOnly cookies and forwards the access token as a bearer token. The web drops `AEP_API_TOKEN` (assumption: the owner did not answer this point); API tokens remain for CLI and automation. Rejected: database sessions (owner preferred signed tokens); JWT without the per-request membership check (disabling would lag up to 10 minutes); scrypt (OWASP ranks Argon2id first and Node now ships it, so no dependency is added); OIDC only (a local demo would need an identity provider, against the PRD portability requirement (v0.1 §7, v0.2 §13)). Revisit for per-tenant SSO, MFA, or a second service that verifies tokens (asymmetric signing would then fit better). Implementation: `authService` and `bearerIdentity` (`packages/application/src/auth`), `Argon2PasswordHasher` and `JwtAccessTokens` (`adapters/identity/local`, `jose`), `password_credentials` and `sessions` (migration 0008; no RLS, like `api_tokens`, because they are read before the tenant is known). `POST /v1/auth/login`, `/refresh` and `/logout` exist only when `AEP_AUTH_METHODS` includes `password` and `AEP_ACCESS_TOKEN_SECRET_FILE` is set; `GET /v1/me` and `POST /v1/auth/password` sit behind the bearer check, and they are the only routes a principal whose password must change can use (others answer 403 `password_change_required`). Tenant administration (`memberService`, `PostgresMemberRepository`, migration 0009) needs `member:manage`: `GET/POST /v1/members`, `PATCH /v1/members/:userId` (role, disabled) and `POST /v1/members/:userId/password-reset`; creating a member or resetting a password returns a random 24-character initial password once (`cache-control: no-store`) that must be changed at first login. A change that would leave the tenant without an active admin is a 409; the transaction locks the tenant's active admins in a fixed order first, so concurrent demotions cannot both pass. Disabling a member or resetting the password ends the member's sessions in the same transaction. `users` now has row-level security: reads and inserts stay open (login runs before the tenant is known), but an update reaches only members of the current tenant. `audit_events` (append-only, tenant RLS) records member changes, password changes and login outcomes of known accounts with the actor and subject, never a password; an unknown email has no tenant to record under. `GET /v1/audit-events?after=<id>&limit=<n>` serves it to admins. A required password change gates password sessions only; an API token of the same member keeps working, since it is a separate credential handed to the member. Web login (`apps/web`): `proxy.ts` (Next.js 16's renamed middleware) runs before every route except `/login` and `/healthz`, refreshes an access token that is missing or within 30 s of expiry and passes the new one to the render it lets through, sends people without a session to `/login?next=…` (only same-site paths are followed after login) and, while the password must change, to `/password`. Cookies are `aep_at`, `aep_rt` and `aep_mcp`, HttpOnly and SameSite=Lax, and Secure with the `__Host-` prefix unless `AEP_SECURE_COOKIES=false` (Compose sets it, being plain HTTP on 127.0.0.1). Pages hide controls the role cannot use, from the permissions `/v1/me` lists; the API still decides. Concurrent refreshes from one browser: the refresh token replaced last still answers for 10 s with an access token only, without rotating or revoking (migration 0010 `sessions.rotated_at`); after that it means a copy was stolen and the session is revoked. This trades a 10-second replay window for not logging people out when two requests refresh at once; the proxy cannot deduplicate refreshes itself because Next.js does not promise it shared state. Compose passes the signing secret as a secret from `AEP_ACCESS_TOKEN_SECRET`. Admin pages: `/admin/members` and `/admin/audit` answer 404 to anyone without `member:manage`. An issued initial password comes back as the server action's result (`useActionState`) and is shown once on that page; it is never put in a URL, so it stays out of history, logs and referrers. OIDC (owner decisions 2026-11-14: `openid-client` 6.9.0, MIT; the API exchanges the code so only it holds the client secret): `OpenIdProvider` (`adapters/identity/oidc`) runs the authorization code flow with PKCE (S256), state and nonce; openid-client verifies the ID token's signature against the provider's JWKS and its issuer, audience, expiry and nonce. Only a literal `email_verified: true` counts. `POST /v1/auth/oidc/start` returns the authorization URL and the one-time checks, which the web server keeps in an HttpOnly cookie (`aep_oidc`, 10 minutes, cleared after one callback); `/login/oidc/callback` posts the provider's query and the checks to `POST /v1/auth/oidc/callback`. `oidc_identities` (migration 0011, no RLS like `password_credentials`) binds (issuer, subject) to a member, at most one subject per member and issuer, so a reassigned email at the provider cannot take over an account bound earlier. A first login finds the member by email through `password_credentials`, which every admin-registered member has and which carries the tenant (memberships cannot be read before the tenant is known). Failed OIDC logins of known members are audited with `method: oidc` and a reason (`unverified_email`, `subject_mismatch`, `disabled`). `GET /v1/auth/methods` tells the login page which methods are on. Configuration: `AEP_AUTH_METHODS=oidc` (or `password,oidc`), `AEP_OIDC_ISSUER`, `AEP_OIDC_CLIENT_ID`, `AEP_OIDC_CLIENT_SECRET_FILE`, `AEP_OIDC_REDIRECT_URI`, optional `AEP_OIDC_NAME`; an http issuer needs `AEP_OIDC_ALLOW_HTTP=true` (local tests only). Tests use navikt/mock-oauth2-server 6.1.5 (MIT, pinned by digest) through Testcontainers and in `compose.e2e.yaml`, never in the quickstart.

ADR-012 Proposed 2026-11-15 (owner decision on the product, PRD v0.2; technical shape to be confirmed in Sprint 5): own chat workspace. The chat lives in this platform's web UI and API, not in Claude or Codex apps, so initiatives, data, approvals, PRs and effect checks stay on one screen. A chat turn calls a model through a new `ModelPort` (messages, tool calls, streaming), kept apart from `AgentPort`, which drives a coding agent in a sandbox. Model endpoints are limited to an allowlist of APIs whose terms exclude training on inputs (Anthropic API, OpenAI API, and their Bedrock and Vertex AI routes); keys follow ADR-007. Tool calls from the model go only to the connector gateway (ADR-013). Turns run in the worker through the job queue (ADR-003), so a long tool call does not hold an API request. The worker appends reply chunks as thread events; the web reads them with the cursor API that mission events use today (`GET /v1/missions/:id/events?after=`), and Sprint 5 decides whether server-sent events replace polling for typing latency. Rejected: adding to Claude or Codex apps (owner wants one screen and their own permissions model); running chat inside the coding sandbox (minutes of start-up per turn, and the sandbox is for untrusted code). Revisit if turn latency through the queue is too high. Implementation (Sprint 5, #43): `ModelPort` (`packages/application/src/models`) streams text deltas, complete tool calls and one `finished` event (stop reason, usage, the model that answered); failures are `ModelCallError` with `retryable`. Adapters: `@aep/model-anthropic` on `@anthropic-ai/sdk` 1.8.0 (beta Messages endpoint, `fallbacks: "default"` with `server-side-fallback-2026-07-01` for the models that take it) and the in-process `fakeModel` for tests and CI; both pass `modelPortContract`. The allowlist is `ALLOWED_MODEL_ENDPOINTS` (`https://api.anthropic.com` only for now); the worker exits before connecting anything when `AEP_MODEL_PROVIDER` or `AEP_MODEL_BASE_URL` is off it. Posting a message enqueues `thread.reply` in the same transaction; the job runs as the person who asked (so RLS applies), writes `reply.started` per attempt, `reply.delta` pieces (about every 250 ms or 200 characters), then the reply as a message with `in_reply_to` (one per message, migration `0013_thread_replies`) and `message.created`; a refusal, an empty answer, a rejected request or a dead job writes `reply.failed`. Defaults: `claude-sonnet-5-5` (`AEP_CHAT_MODEL`) at effort `low` (`AEP_CHAT_EFFORT`); a tenant admin may choose another model for the tenant (`/v1/settings/chat`, permission `settings:manage`, migration `0015_tenant_settings`, audited as `settings.chat_model_changed`) from `CHAT_MODELS` (`claude-sonnet-5-5`, `claude-opus-5-5`, `claude-haiku-5-5`), all on the instance key until ADR-007; the worker reads the choice per reply and ignores a stored model that is no longer listed. Sprint 5 decisions (owner, #43): the effort is chosen per message in the UI (speed first `low`, the default; standard `medium`; thorough `high`) and stored on the message; the reply records the model that answered (`model`, which differs after a fallback); the model sees the latest 500 messages up to the one it answers. The web keeps polling the events (every second, `/threads/:id/events`) rather than server-sent events: a reply arrives in pieces of about 250 ms, so polling adds at most a second before the first piece; revisit if that feels slow.
ADR-013 Proposed 2026-11-15 (owner decisions 3 and 7, PRD §5): connectors through MCP with a gateway. A connector is a declarative manifest (MCP server URL or container image, auth method, allowed tools with read/write class, egress hosts, a source URL per claim), validated by schema. Connections are personal (tenant × user × connector) by default; a tenant connection (tenant × connector) serves unattended work such as monitoring and, if the admin allows it per connector, stands in for a person without their own connection. OAuth tokens, or static keys where the admin allows them, are stored encrypted with AES-256-GCM under the instance master key (the same mechanism as ADR-007), returned by the API only as status (connected, expired, connected-at). The connector gateway runs in the worker, decrypts the token, calls the MCP server and returns only the tool result; neither the model nor any agent sandbox sees a token. Local MCP servers run as containers the gateway starts with the egress hosts of their manifest. Write, delete and send tools need a human approval per call; every call is audited with user, connection, tool and class. Disabling a user deletes their tokens and asks the provider to revoke them. Tests and CI use mock MCP servers, never real company accounts. Rejected: giving agents short-lived tokens in the sandbox (a prompt-injected agent could exfiltrate them); one shared company connection for chat (the AI would see more than the person); hand-written UI per connector (the manifest drives shared components). Revisit when a service has neither MCP nor an OpenAPI description. Sprint 6 decisions (owner, #52): OAuth clients are registered dynamically (RFC 7591) once per connector, server and redirect URI. The MCP spec of 2026-07-28 deprecates this in favour of Client ID Metadata Documents, which the authorization server fetches from outside; deployments closed to inbound traffic cannot offer that, so registration stays dynamic until #56 adds metadata documents (before 2027-07-28, the earliest removal the MCP TypeScript SDK states). The worker, not the API, exchanges the authorization code and seals the tokens, so neither the master key nor a token enters the API; the API registers the client and builds the authorization URL, which involve no secret. Write tools are approved in the thread, call by call; a reply makes at most 10 tool round trips, each call has 60 seconds, and a result is cut at 50,000 characters. Containers for local MCP servers wait for v0.4. The Amplitude manifest asks for `all:read` and `offline_access` only and allows read-only tools; a tool that reads or writes depending on its arguments counts as write. Implementation (connections, #52): manifests live in `connectors/<id>/manifest.json`, validated by `@aep/connector-manifests` (zod, unknown keys rejected) and by `manifestProblems` in the domain; `checkToolCall` and `checkEgress` are the gateway's per-call checks. `SecretSealer` and `SecretOpener` are separate ports; `@aep/secrets-local` implements AES-256-GCM (`v1.<key id>.<iv>.<ciphertext and tag>`, the row as additional authenticated data) under a 32-byte key read from `AEP_MASTER_KEY_FILE`, which only the worker reads. `@aep/connector-mcp` runs discovery (RFC 9728, RFC 8414), registration, the authorization code grant with PKCE S256 and a resource indicator, refresh and revocation (RFC 7009) on the MCP TypeScript SDK v2 (`@modelcontextprotocol/client` 2.4.0), with every request limited to the manifest's egress hosts and no redirects followed. Migration `0016_connections`: `connector_clients` (shared, no tenant data, no RLS), `connection_authorizations` (PKCE verifier and, once answered, the code, for the person only), `connections` (status, for the person, or for an admin transaction that sets `app.connection_admin`) and `connection_tokens` (sealed tokens, for the person only, even for admins). The API (`/v1/connectors`, `/v1/connectors/:id/authorize`, `/v1/connections/oauth/callback`, `DELETE /v1/connections/:id`; admins `GET /v1/admin/connections`, `DELETE /v1/admin/connections/:userId/:connectorId`; permissions `connector:use` for members who post, `connector:manage` for admins) stores the answer and enqueues `connection.exchange` in one transaction; the worker exchanges, seals and audits `connection.connected`. Disconnecting, by the person, an admin, or disabling the member, marks the connection and enqueues `connection.disconnect`, which revokes the refresh and access tokens at the provider, deletes them and audits `connection.disconnected` (if revocation keeps failing, the dead-job handler deletes the tokens anyway and records `revoked: false`). Configuration: `AEP_CONNECTORS_DIR`, `AEP_CONNECTOR_REDIRECT_URI` (the web UI's `/connections/oauth/callback`), `AEP_MASTER_KEY_FILE` (worker; required with connectors, or it refuses to start), `AEP_CONNECTORS_ALLOW_HTTP=true` for the mock server in tests only. Tests use `@aep/mock-mcp`, shaped like Amplitude's server. Web (`apps/web`): `/connections` lists the connectors with the person's status and starts an authorization through a server action, which sends the browser to the provider; `/connections/oauth/callback` (behind the login proxy) forwards the query to the API and shows nothing from it; the page reads itself again every second while a connection is connecting or disconnecting, for at most a minute. `/admin/connections` (404 without `connector:manage`) lists members' connections by status and disconnects one. Compose: connectors are off unless `compose.connectors.yaml` is added, which turns them on for the API and the worker and passes `AEP_MASTER_KEY` to the worker as a secret (Compose refuses an unset secret variable, so the quickstart without the file needs no key). The browser tests add the mock server as a service (`compose.e2e.yaml`, image target `mock-mcp`) reached as `mock-mcp.localhost`: the MCP SDK sends a token over plain HTTP only to a loopback name, and browsers resolve `*.localhost` to 127.0.0.1; `tools/mock-mcp/connectors` holds its manifest. Gateway (#52, E1): `connectorGateway` (`packages/application/src/connectors/connector-gateway.ts`) runs in the worker and is the only code that opens a person's tokens. For a reply it offers the model the tools that are both listed by the server and declared `read` in the manifest, named `<connector>__<tool>`, through the connections of the person who wrote the message; write tools are neither offered nor called (refused and audited) until approval in the thread exists, so text read through a connector cannot cause a write (scenario I). Each call is checked with `checkToolCall`, limited to 60 seconds, cut at 50,000 characters and audited as `connector.tool_called` (person, connector, tool, class, outcome, thread, duration, result size; never arguments, results or tokens; migration 0017). An access token within 30 seconds of expiry, or one the server answers with 401, is refreshed once; the new tokens replace the old only if the stored access token is still the one read (a concurrent refresh wins and its tokens are used), and a refused refresh token (`invalid_grant`) marks the connection `expired`. `@aep/connector-mcp` `mcpTools` opens a Streamable HTTP session per operation with the SDK `Client`, through the same egress-checked fetch, the token in the transport's auth provider only. The reply loop (`replyToMessage`) makes at most 10 tool round trips, then ends the reply with what it has and records `reply.limited`; tool results go to the model only, marked in the system prompt as data and not instructions. Thread events record `tool.called` (with the person whose connection was used), `tool.finished` (outcome, truncated) and `connector.unavailable`, never result content; `message.created` lists the connectors a reply drew on in `sources`. Tool calls repeat when a reply job is retried, which only reads again. The fake model calls a tool named by a `/tool <name>` message, for the browser tests. Write approval (#52 decision 2, E2): with an approval repository the gateway also offers the manifest's write tools, described as needing the person's approval. When the model calls one, the reply runs the round's read calls, then pauses: `reply_pauses` keeps the state to continue from (the turns after the thread's messages, the round's read results, the text so far; it holds data read through the connection, so only the person who asked can read the row, and the snapshot is dropped when the pause closes) and `tool_approvals` one row per write call with the exact arguments (migration 0018). The thread gets `tool.approval_requested` with the arguments as JSON; arguments over 4,000 characters cannot be shown in full, so such a call is answered as refused instead. Only the person who asked, whose connection the call uses, decides (`POST /v1/threads/:id/tool-approvals/:approvalId`, `connector:use`); other members who can read the thread see the card without buttons. Each decision appends `tool.approval_decided` and an audit event `connector.tool_decided`; the last one enqueues the continuation (`thread.reply` with `pauseId`) in the same transaction. The continuation runs approved calls through the gateway, which runs a write only after claiming its approval (approved to executing, matched on connector, tool and arguments as jsonb) and marks it done whatever the outcome, so an approved call runs at most once: a call left claimed by an interrupted attempt is reported to the model as of unknown outcome and not run again. Declined calls are answered as declined. A first attempt does nothing while a pause for its message is open, so a retried job does not ask twice. Expiry (owner, 2026-11-16): a write call nobody decides within three days expires (`APPROVAL_TTL_MS`; a card left on a Friday evening still stands on Monday). Waiting longer would let someone approve arguments built from data that may have changed, approve without remembering the context, and keep data read through the connection in the paused state. The pause enqueues `thread.approval_expiry` with `runAfter` in the same transaction; it marks what is still pending `expired` (migration 0019), records `tool.approval_decided` with decision `expired` and the audit event, and enqueues the continuation, which tells the model nothing changed. The card shows the deadline. GitHub code read (#52 scope 7, owner decision 2026-11-17): a workspace lists the GitHub repositories its chat may read (`workspace_repositories`, migration 0020: tenant row-level security, unique per workspace ignoring case, names checked by the database). Admins add and remove them (`PUT` and `DELETE /v1/workspaces/:id/repositories/:owner/:name`, `settings:manage`, audited as `workspace.repository_added` and `workspace.repository_removed`); members who read missions list them (`GET /v1/workspaces/:id/repositories`); there is no screen yet. When the worker has the GitHub App (`AEP_GITHUB_APP_ID`, `AEP_GITHUB_PRIVATE_KEY_PATH`), a reply in a thread of a workspace with repositories offers two read tools, `github__search_code` and `github__read_file` (`workspaceCodeTools`, `packages/application/src/git/code-tools.ts`); a connector manifest with the id `github` then stops the worker at start. They read through the instance's App, not a person's connection: the repository the model names is matched against the workspace's list on every call, so another repository is refused and audited like an undeclared connector tool. Paths must be relative without `.` or `..` segments, refs are branch, tag or SHA names, and search queries may not carry `repo:`, `org:`, `user:`, `owner:` or `enterprise:`, which would widen the search. Calls share the connector limits (60 seconds, 50,000 characters) and audit (`connector.tool_called` with `repository`). `@aep/git-github` `gitHubCodeReader` uses the contents endpoint (files up to 1 MB as text; binary and larger files are reported, not returned) and code search (default branch, files under 384 KB, 10 searches a minute), both with an installation token limited to the one repository and `contents: read`, reused until five minutes before it expires. `tool.called` carries `via: "github_app"` and the repository; the web shows the call as read through the workspace's GitHub App. `sources` lists `github` when a reply drew on code.
ADR-014 Proposed 2026-11-15 (owner decision 6, PRD §9): personal threads and sharing. A thread has an owner and a visibility (personal, shared with chosen members, or the whole workspace). Row-level security filters threads and messages by tenant and by user: the request sets `app.user_id` next to `app.tenant_id` (`adapters/persistence/postgres/src/tenant-session.ts` sets only the tenant today), and the API checks the same rule, so neither alone is the only control. Results from personal connections carry a source label (connector, user). Sharing a thread or creating an Issue from it first lists those results; the default is to share as-is and items can be excluded. Rejected: tenant-wide threads by default (personal connections would leak to members without access to the source tool); blocking sharing of personal-connection data (owner chose share-as-is after confirmation). Revisit if regulated tenants need sharing blocked per connector. Implementation (Sprint 5, #43): migration `0012_threads` adds `threads`, `thread_members`, `thread_messages` and `thread_events` (the last two append-only); `withTenantUser` sets `app.user_id`, and with no user set no thread is visible. A thread belongs to a workspace; `workspace` visibility means every member of the tenant, because memberships are per tenant. Anyone who can read a thread may post in it; only the owner changes its visibility, and going back to personal deletes the member rows. `thread_members` repeats the owner so its policy does not read `threads`, whose policy reads `thread_members`. Viewers read threads shared with them but do not create or post (`thread:read`, `thread:write`).
ADR-015 Accepted 2026-11-15 (owner decision): one organization per instance. The primary deployment is an instance per organization, on its own infrastructure, with keys the organization creates; tenants of one instance therefore do not share data, keys or databases in practice. The tenant boundary stays in the code (`tenant_id` on every tenant-owned row, row-level security by tenant, tenant-scoped authorization, cross-tenant tests) as defense in depth and for later uses: business units of one organization in one instance, or a hosted offering. Separation between members of one organization does not depend on this and stays required: personal threads and personal connections are filtered by user (ADR-014, ADR-013). Consequences: ADR-007's tenant key and instance key are the same key under this model, so its question whether a tenant may forbid the instance key no longer arises; the production isolation tier (shared database with RLS or a database per tenant) is a database per organization; the per-tenant model choice (ADR-012) is the organization's choice. A hosted offering with mutually untrusted tenants (T2) is not planned; it would need this ADR revisited together with ADR-005's isolated execution. Rejected: removing tenants from the schema (little saved, and the boundary is cheap to keep and costly to add back).

## 10. Quality gates for architecture changes
Changes to ports require versioned contract tests across all supported adapters. Database schema changes require forward/backward migration tests. New provider requires cancellation, timeout, tool approval, streaming, error mapping and credential-leak tests. Security-sensitive change requires threat model update and reviewer approval. CI cannot be bypassed by agent-authored code.
